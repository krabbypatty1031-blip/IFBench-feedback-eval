## 目标与交付

复用固定版本的官方数据、生成接口和评分器，比较两个模型在 B0 初始回答、B1 自我检查、B2 整体反馈和 B3 约束级反馈下的表现。交付可复现的数据划分、代码和配置、冻结记录、原始输出、量化分析、人工审核及报告素材。新增代码和运行产物放入独立目录，保留官方源文件及许可；具体文件名在实现时确定。

## 执行顺序

### Task 1：核验环境与官方基线

- 记录 Git 提交、Python 版本、依赖锁文件、NLTK 数据路径与官方数据 SHA-256；检查 300 个 ID、重复提示和两份数据差异。
- 指定 `data/IFBench_test.jsonl` 为唯一数据源。设置 `NLTK_DATA` 后运行官方测试及官方样例评分，检查 strict/loose 文件和逐条结果。
- 交付环境核验记录与可重复命令；验收：环境和数据可识别、官方测试与样例评分可复现，异常有记录。不得使用正式测试题进行提示调整。

### Task 2：审计数据与确定划分

- 离线分析约束种类、单/双约束、重复和可识别同源任务；以确定性规则及固定种子产生候选 40 开发、260 测试，按同源组隔离。无法确认同源关系的情况记录限制，不宣称彻底隔离。
- 生成 ID 清单、抽样规则、组别、数据与划分哈希；保证每题恰属一组且无 ID 交叉。若组结构不允许精确配额，记录实际数量与原因。
- 验收：无重复、无交叉、数据文件不变，分组与约束分布可审计；开发和正式测试的用途明确。

### Task 3：验证器与反馈适配

- 调用官方 strict/loose 评分，不复制或重写官方判分规则；建立题目 ID、约束、参数和逐条评分的映射。开发集核验 58 种约束及其依赖，涉及正式测试内容的处理只做固定规则的离线结构审计，不用输出调整提示。
- 实现整体反馈与约束级反馈：仅使用 strict 判定、可验证的原任务要求，不猜测错误原因。确定无法可靠映射、验证器异常、缺失资源的明确状态及处理办法；反馈不得暴露额外标准答案。
- 验收：通过/失败、双约束、异常和空输出等代表性案例匹配官方结果；错误状态与失败判分分开，无法映射的样本不会产生虚构反馈。

### Task 4：模型客户端与调用记录

- 基于官方兼容接口增加模型适配、独立消息分支、超时、限制并发、有限重试和响应记录；参数兼容性、模型版本、终止原因、token、延迟和费用未知值均显式记录。密钥从环境读取，不写入日志。
- 定义唯一身份：协议版本、模型、题目 ID、条件、轮次；避免官方按 prompt 续跑造成不同条件混用。冻结配置与指纹、原子保存、可审计的断点续跑；配置变化拒绝混用旧记录。
- 支持开发和正式结果分目录，并对 API 失败、限流、超时后计费不明、截断、空回答及验证异常分别记账；任何可能发生的费用纳入同一已核实的全局额度。当前工作区是否存在此前账本、可用余额和各模型单价均须实际核对，不存在时不得假装额度或历史支出为零。
- 验收：模拟客户端覆盖成功、失败、重复、异常续跑及配置冲突；不调用外部模型即可验证记录完整和预算控制。

### Task 5：实现 B0–B3 实验流程

- B0 仅调用一次；B1/B2/B3 从同一原题和初始回答独立分支，各一次修订，初始通过与失败均执行。保存完整输入、输出、验证结果和反馈来源。
- 开发集设计各组提示词，除反馈本身外保持消息结构及修订次数一致；B2/B3 在通过时允许原样返回。输出格式不额外强制可能破坏被测约束的包装。
- 验收：模拟模型可证明各分支无串联、反馈与题目匹配、通过样本同样进入修订；条件身份、模型参数和输入输出可追溯。

### Task 6：开发试验与预算评估

- 先离线端到端检查，再用开发集的一小部分验证两个候选模型实际 API、输出格式、截断、验证反馈和用量；随后在可用额度内按需扩展到开发集。开发结果仅用于调整协议，不纳入正式结果。
- 比较条件分布、失败原因与区分度；估计正式 260 × 2 × 4 = 2,080 次输出的 token、费用、耗时，并加入技术重试及不确定费用。必要时在查看正式结果前缩小范围。
- 验收：可用模型与参数、实际开销、测试范围、重试规则和成本上限形成记录；无法连接、无法映射或表现饱和时按协议调整或如实报告。

### Task 7：冻结实验

- 固定代码提交或变更快照、依赖、原始数据和划分、模型标识、提示模板、参数、strict/loose 口径、反馈规则、错误与缺失数据处理、人工抽样、预算与重试上限；计算哈希并写冻结记录。
- 复查每项结果都能关联版本；开发和测试分开，变更协议时使用新版本及新目录。
- 验收：他人可根据冻结记录重建条件；正式运行不会采用未冻结配置或覆盖先前结果。

### Task 8：正式运行与质量控制

- 运行两个模型、测试题和全部条件，依据冻结协议控制预算、并发与断点。保留原始响应、逐条验证、API 状态和计量数据；不根据中间结果调整提示或选择题目。
- 验收：各模型、题目和条件的预期数量与实际状态可核对；成功、失败、截断、缺失及费用不明均有单独汇总，未完成样本如实报告。
- **完成情况：** 2080 身份均已记账。4096 原始账本 success 1891 / empty 53 / error 136。费用 unknown。

### Task 9：量化分析与人工审核

- 严格提示级通过率为主指标；报告 strict/loose 的提示级和约束级结果、修复率与退化率的分子分母、覆盖与缺失、成本和延迟。按相同题目配对，以题目或已识别同源组重采样计算差异区间；类别及单/双约束分析标记探索性。
- 正式运行前固定审核抽样规则和种子：约 40 道题，覆盖模型与全部条件，隐藏身份、打乱顺序；依据原任务标记完成、部分完成、未完成或无法判断，保留审核记录和分歧。仅一名审核者时披露限制。
- 验收：统计可以从原始记录重新生成；图表标示分母和缺失；规则得分、内容质量与模型加验证器成本分开解释。
- **完成情况：** `analysis.json` 已从记录重建（正式表覆盖 16384/32768 恢复正文）。320 条盲审包已生成；`judgments.csv` 未填。

- 结合课程要求完成背景与相关工作、研究问题、方法与复现实验设置、定量结果、成功与失败案例、局限、个人贡献和 IEEE 参考文献；制作展示材料。
- 保留 IFBench 代码和数据的署名及许可说明，区分原项目与本项目贡献；不将公开数据描述为保证未被模型训练使用，也不将反馈系统得分当成模型独立能力。
- 验收：报告所有主结论能追溯到运行与分析记录，图表与正文一致；形成提交用报告与 PPT PDF。
- **完成情况：** 未开始。
